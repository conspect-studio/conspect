# Experimental exchange protected-media wire v2

This is the **single canonical** experimental adapter adopted from `039702d5` and changed incompatibly to `MC02`/`MG02`. Old `MC01`/`MG01` bytes are rejected, never downgraded. `PAID_DELIVERY_ENABLED=false`. No HTTP issuer, persistent nonce-store implementation, native encrypted HEVC/audio decode, connected-session denial/queue-flush measurement, or production trust configuration exists here. This library and its offline fixture are **not** paid-delivery evidence.

## Scope and MoQ seam

The MoQ fixture currently carries `Packet{payload,pts_us,verified_rap}`, `Window{generation,packets}`, UTF-8 track names (`video`, arbitrary audio names). Video creates a group at verified RAP; audio creates one group per packet. The hook owner must expose actual monotonic `u64` group and object IDs and publisher generation. Encrypt the **whole serialized hang object**, including hang timestamp/framing, after serialization and before publication. Decrypt before hang parsing and before HEVC/AAC decoder submission. This crate does not number MoQ groups or objects; supplied identity must match the transport object's identity exactly. No plaintext fallback when an MC02 object or grant is missing. MoQ transport integration is not in this commit.

## Media MC02

All integers are unsigned big-endian. UUIDs are raw 16-byte values. Header (AAD) is:

| Offset | Size | Field |
| --- | ---: | --- |
| 0 | 4 | ASCII `MC02` |
| 4 | 16 | version ID |
| 20 | 16 | feed ID |
| 36 | 16 | publisher instance ID |
| 52 | 8 | epoch `floor(Unix ms / 5000)` |
| 60 | 4 | publisher generation |
| 64 | 8 | *seal counter* reserved durably before encryption, independent of MoQ numbering |
| 72 | 8 | MoQ group ID |
| 80 | 8 | MoQ object ID |
| 88 | 8 | capture Unix milliseconds |
| 96 | 1 | UTF-8 track-name byte length (1..64) |
| 97 | variable | UTF-8 track name; reject controls |
| after header | variable | AES-256-GCM ciphertext followed by 16-byte tag |

HKDF-SHA256 derives a track-specific AES-256 key from the **independent, random current-epoch 32-byte root** using info `exchange-MC02-aead-key\0 || version16 || publisher16 || epoch8 || tracklen1 || trackbytes`; nonce is publisher-generation BE4 || durable seal-counter BE8. The full header is authenticated as AAD. Maximum plaintext 16 MiB and at most 32 tracks per epoch. Receiver checks the independently observed transport track/group/object/capture identity, version/feed/publisher/generation/epoch, ciphertext tag, capture age and monotonic seal counter per track. A late join can start at any counter; older out-of-order objects are deliberately discarded. Use `Receiver::renew` in place for same-epoch grants: it verifies pinned issuer, all identities and unchanged root key, rejects expiry rollback, and preserves replay high-water. `Receiver::deny` is irreversible. Reconstructing `Receiver::accept` from the same grant on reconnect resets replay state: the embedding runtime MUST persist per-(booking,epoch,track) replay high-water and deny state across reconnections; this adapter alone does not implement cross-process replay persistence. Decrypt errors never disclose plaintext.

`CounterReservation` is an injected interface. `DurableCounterJournal` is an opt-in, single-host local implementation: it serializes writers on a stable exclusive `.lock` inode, bounds 4096 records, writes a `create_new` stage, fsyncs the stage, renames to the journal, and fsyncs the parent directory BEFORE returning a counter. It rejects duplicate scope records, generation/epoch rollback and overflow; a leftover staged file or corrupt journal fails closed. Never delete/replace the stable lock inode while any publisher runs. Place journal and lock in an owner-only directory on a reliable local filesystem with working file and directory fsync; it cannot detect a privileged attacker restoring an old journal snapshot, so an external durable anti-rollback source is mandatory under that threat. No epoch key material is stored in the journal. A new publisher generates an independent random root per epoch; NEVER reconstruct with a retained root and reset counter. The fixture-only in-memory counter is NOT durable. No future-epoch root is derived from a granted root; do not prefetch future keys.

## Grant MG02

Body exactly 200 bytes plus 64-byte Ed25519 signature over those 200 bytes. Offsets: `MG02`4; fixed issuer `conspect-exch-v2`16; fixed audience `conspect-engine2`16; booking16; taker organization16; feed16; version16; engine16; publisher16; authorization generation8; publisher generation4; epoch8; issued Unix ms8; expiry Unix ms8; raw epoch root key32. The pinned verification public key is injected out-of-band; use a dedicated exchange issuer, never the licensing key. `Receiver::accept` verifies the signature and *independently expected* booking/taker/feed/version/engine/publisher/both generations plus current epoch, issuance/expiry and uncertainty. Current epoch only. `Publisher::grant` takes `active` as a caller-supplied authority assertion: the authenticated web authority must transactionally validate booking state, organization and engine membership, current authorization generation, credit, release state and epoch on **every** key issuance. Neither this crate nor its test signing key is an implemented web endpoint. Grant contains a secret: authenticated TLS only, `Cache-Control: no-store`, no logs or catalogue exposure.

Denial calls `Receiver::deny()` and wipes key; runtime must also fence queued encoded, decoded, audio and render media and stop usable receipts. The library enforces expiry with zero post-expiry grace and bounded capture age, but already received plaintext or keys cannot be revoked. Honest cutoff upper bound includes remainder of current 5-second epoch, downstream queue/decode/render latency, clock uncertainty and grant issuance race. No five-second cutoff claim is justified before native connected-session measurement.

## Protected publisher key path

`Publisher::new` draws its epoch root locally from the OS CSPRNG and is **test/fixture only**: a restart produces a *different* root for the same epoch, which is exactly what protected delivery must not do. A protected publisher uses `Publisher::from_authority`, which takes the current epoch root from an injected `AuthorityRootProvider` and binds the durable counter scope before anything can be sealed. `Publisher::key_source()` reports which path was taken; `Publisher::bound_scope()` reports the bound `(version, publisher, epoch, publisher_generation)`.

The provider MUST: generate the root once with a CSPRNG for `(org, version, publisher_machine, server_generation, epoch)` and keep it encrypted at rest; return the **same** root on every retry of that scope; return the **current** epoch only (never a future one, never a derived or prefetched key); assign `server_generation` monotonically for the identity; never accept a caller-supplied root; and never log the root. The grant already carries the root, so the root is secret material — authenticated TLS only, `Cache-Control: no-store`.

`from_authority` fails closed before any seal unless: every identity in the returned context is the one asked for (`Error::Denied`); the epoch is the current one and the context is neither stale nor late — `issued <= now`, `expiry > now`, both inside the epoch (`Error::Expired`); the `u64` server generation fits the `u32` wire field (`Error::GenerationOverflow`, **never truncated** — a truncated generation would collide with another scope's nonce space); and the process's `AuthorityRootGuard` sees a generation that is not below the highest it accepted (`Error::Replay`), with no second root for a scope already seen (`Error::Denied` — authority equivocation). The server generation is *assigned*: no constructor takes it from the caller.

One guard per process. A retry at the same generation and epoch is legitimate and **continues** the durable counter — the journal scope is `(version, publisher, epoch, generation)` — so a restart with the same committed root resumes where it stopped. The guard's `(version, publisher)` identity axis matches the durable journal's scope; neither provides cross-host coordination. A journal restored to an older snapshot cannot be detected locally, so the authority MUST issue a **fresh generation** whenever it cannot prove the publisher's counter state is ahead: a new generation is a new nonce scope **and** a new root, so no `(key, nonce)` pair can repeat. A generation below the journal's high-water is refused as `Error::Replay`. None of this changes MC02/MG02 bytes: `tests/authority_root.rs` asserts the protected path emits the published cross-language vectors byte for byte.

**Lease client and local fence.** The client half of that lease is implemented in `src/authority_http.rs` against the frozen amendment, with an injected transport and no live endpoint: `PublisherLease::acquire/renew/release` call `POST .../publisher/lease/acquire|renew|release` with the exact frozen bodies, and the root route `GET .../publisher/current-epoch` now carries `Exchange-Publisher-Lease` and `Exchange-Publisher-Boot-Nonce`. The generation is **authoritative and opaque**: every acquire — including the first — assigns one, an adapter never guesses an initial value, and a lower answer is refused (`Error::Replay`). A live re-acquire is not sent (the contract answers `409`), a lost or revoked token never renews, and `409 lease_required` / `404` stale-lease on the root route latches the local fence closed for this boot nonce. The boot nonce is 16 CSPRNG bytes per process, never persisted. The local seal deadline is monotonic and derived from the server expiry **minus** clock uncertainty (bounded, default 1 s), and the server's `notBeforeMs` **plus** uncertainty gates the first seal of a takeover root, so a new root never encrypts before the previous epoch's tail ended. `PublisherLease` implements `LeaseFence`; `Publisher::from_authority` takes that fence from the `AuthorityRootGuard` and re-checks it on every `encrypt` and every `grant`, and a protected (`KeySource::Authority`) publisher built without a fence refuses to seal (`Error::Denied`) — the fence is checked on the seal, not only on the fetch. `revoke`/`release` therefore stop old-key encryption immediately, but they do not retract a root already returned to a host: the authority's server-side revocation and the native connected cutoff remain required. `acquire`/`renew` are control-plane calls and must never run on the output clock.

**Opaque HTTP resource ids are not the crypto identity.** The authority addresses a publisher with opaque strings — an organisation id such as `org_<uuid>`, an exact version id string, and an arbitrary machine id such as `mch_...` — while this library binds raw 16-byte identities. `HttpResourceIds` carries those exact strings for the path, query and body, and `CryptoBinding` carries the separately registered raw `org`/`version`/`publisher_machine`. No id is stripped, parsed, hashed or coerced into the other form, and no constructor derives one from the other: every request is assembled with the URL API so each id is one percent-encoded segment or one percent-encoded query pair (a literal `+`, space, `/`, `?`, `#`, `&` or `=` can neither escape the prefix nor add a parameter), ids must be non-empty, control-character-free and bounded (`MAX_ID_CHARS`), and every id echoed in a response must equal the exact string sent. The authority's CSK → (opaque ids, crypto binding) mapping is checked by the authority at registration; a missing or mismatched mapping is refused rather than repaired, and a lease paired with different ids or a different binding than the provider's is refused before any request. The epoch-root context is built from the explicit `CryptoBinding` only, after the authenticated response has been matched to the opaque ids; `tests/authority_http.rs` proves the sealed MC02 header carries the registered raw version, never an encoding of the opaque string.

**Mandatory single-host lease (transport not implemented by this library).** `AuthorityRootGuard` fences only one process; `DurableCounterJournal` serializes only writers of one host's journal; `PublisherLease` is a client of the authority's lease, not the authority. Two hosts using the same `(version, publisher, epoch, publisher_generation, root)` with independent journals can reserve the same counter and encrypt under the same derived key and nonce. AAD differences do **not** make nonce reuse safe: this is a catastrophic AES-GCM failure. Before issuing a protected root or grant, the authority/deployment MUST lease each publisher identity exclusively to exactly one host for the active version, publisher generation and root; it MUST fence a former host's sealing and future key issuance/media grants before transferring ownership. On failover, issue a **new authoritative publisher generation and fresh root**, never resume the old generation on a different journal. Bound the old key's remaining media/receiver lifetime using the current epoch and downstream queue/cutoff policy; do not claim that lease expiry disconnects an established viewer or revokes ciphertext already received. There is no multi-host lease, distributed fence, or failover enforcement in this crate, so protected paid delivery remains unavailable until that authority/runtime contract and the native cutoff gate are implemented and proved.

## Frozen receiver grant HTTP client (not deployed)

`HttpReceiverGrantClient` sends exactly one `POST /v0/organisations/{orgId}/exchange/bookings/{bookingId}/grants`, with organisation CSK bearer and JSON `{machineId,requestedExpiryMs}` (safe integer Unix ms). Opaque ids are explicit strings, percent-encoded as separate path segments, independent of the authoritative raw `Binding`. The immutable booking authorization generation is **0**; the binding includes the current publisher generation. `Receiver::accept` verifies the dedicated pinned exchange Ed25519 key and every raw identity before the client accepts a grant. A valid signed generation 0 is accepted; signed generation 1 is denied against the generation-0 expectation.

The shared `VerifiedHttpsTransport` supports this binary response without changing the publisher JSON interface: exact MIME `application/octet-stream`, explicit unambiguous `Content-Length: 264`, no transfer/content encoding, actual body exactly 264, bounded read of at most 265 bytes, `private` and `no-store` directives, and no `public` directive. Secret grant storage is zeroized and has no Debug. TLS verification, no redirects, three-second timeout and no secret logging remain required. Non-200 responses fail closed; the server contract is generic 404 for denials, 401 for unauthenticated, and 503 while the gate is off **before key access**. Server behavior is not proved by this client.

The server clamps expiry to min(requested expiry, booking end, current epoch end). The client never expands expiry, rejects an expiry beyond the request, and requires expiry strictly greater than the post-response clock plus 1000 ms. A request may ask beyond the current epoch; acceptance still requires the signed response in the current epoch and no later than its end. There is no fallback or internal retry loop. On near-boundary denial the runtime must wait until `next_epoch_ms(now)` with a timer, a bounded overall deadline and bounded attempts; immediate retries are forbidden. The runtime must obtain the HTTP-to-raw binding mapping from the authority rather than invent one.

No live request was made to this new route. Keep the authority gate OFF and paid delivery false until the web deployment notice, production trust setup, native encrypted runtime/lease integration, and native connected-session cutoff evidence exist. This adapter alone proves none of those conditions.

## Receipt boundary

Web-proposed adapter endpoint: `POST /v0/organisations/{takerOrgId}/exchange/bookings/{bookingId}/receipts` with an org-scoped engine bearer, `{receiptId,sequence,mediaStartMs,mediaEndMs,observedAt,usable,reason?,quality:{bitrateBps,width,height,fps,jitterMs,queueAgeMs,backpressure?}}`. `ReceiptAdapter` validates intervals <=5 seconds and lag <=15 seconds, accepts only a caller-supplied decoder observation, and reserves a sequence through `DurableReceiptSequence` backed by the crash-safe journal. `ReceiptSpool::record_and_queue` MUST run before HTTP delivery: it atomically stores exact ID/sequence/payload AND the last confirmed interval cursor under one owner-only file transaction. Bounded capacity 64 rejects new evidence without cursor advance; an acknowledged record is removed only on exact ID/sequence match, while cursor remains. A crash between sequence reservation and spool commit produces a gap, never an ID reuse or billable interval. Retry ONLY the persisted pending bytes. `usable=true` only on receiver-decoded fresh advancing media; held/slate/outage=false, stationary pixels with advancing decoded timestamps may qualify. Server binds credential org to path+booking, dedupes same ID/sequence, rejects changed payload as conflict, reconciles union of intervals to prevent double billing, and requires a durable run generation. Reports are authenticated assertions, not cryptographic proof. No HTTP adapter, wallet debit or operator token is minted here.
