# Live per-output discrete-track set — design proposal

Status: **proposal, not implemented**. This is an R3 design. A cross-vendor panel must review the transport transition and commit protocol before implementation. It does not claim that `slots.audio` changes apply live today.

## 1. Observed boundary

The current run resolves each configured output's audio selection during pipeline build. `Pipeline::build` derives `discrete_tracks` from the `[audio]` routing document and calls `apply_output_audio_selections` before splitting rate outputs and constructing the run's encoders ([`pipeline.rs:3526-3542`](../../crates/multiview-cli/src/pipeline.rs#L3526-L3542)). That helper updates the `PacketMuxSink` selection for File, HLS and Push, sets Cast's separate `AudioSelection`, and skips WebRTC, NDI and AES67 ([`pipeline.rs:15879-15916`](../../crates/multiview-cli/src/pipeline.rs#L15879-L15916)).

The output then derives each binding's audio stream indexes from the sink selection once and stores them in `output_audio_tracks` ([`pipeline.rs:3634-3676`](../../crates/multiview-cli/src/pipeline.rs#L3634-L3676)). `run_outputs` only publishes whether stream index 0 (program mix) exists; it has no selected-track set or generation ([`pipeline.rs:4131-4165`](../../crates/multiview-cli/src/pipeline.rs#L4131-L4165)). The binding and its window therefore carry a fixed set of audio indexes for the run.

`PacketMuxSink::set_audio_selection` mutates a field on the sink object ([`sink.rs:2058-2075`](../../crates/multiview-output/src/sink.rs#L2058-L2075)); it does not alter a muxer already opened on another thread. `run_av_tracks` reads that selection before registering streams. Single-container File/Push adds video, optional program audio and selected track streams, then writes one header ([`sink.rs:2141-2180`](../../crates/multiview-output/src/sink.rs#L2141-L2180)). The format's stream layout is explicitly pinned after header ([`sink.rs:160-167`](../../crates/multiview-output/src/sink.rs#L160-L167)).

For segmented output, the first HLS segment opens one long-lived MPEG-TS muxer. Later GOPs redirect that same muxer to new segment files, preserving each PID's continuity state; the stream set remains the set registered at initial header ([`sink.rs:3240-3368`](../../crates/multiview-output/src/sink.rs#L3240-L3368)). The `SegmentState` stores the selected tracks and seeds once ([`sink.rs:2364-2375`](../../crates/multiview-output/src/sink.rs#L2364-L2375), [`sink.rs:2882-2888`](../../crates/multiview-output/src/sink.rs#L2882-L2888)). Thus a new selection needs a new mux layout, not only a changed packet filter.

The output-window registry describes opened audio streams (`AudioDescriptor`) and effective output bindings. Its binding is immutable and currently has no selected-track set or audio-set generation ([`output_window_registry.rs:132-168`](../../crates/multiview-cli/src/output_window_registry.rs#L132-L168), [`output_window_registry.rs:183-207`](../../crates/multiview-cli/src/output_window_registry.rs#L183-L207)). Its audio filter has only `All` and `ProgramMix` ([`output_window_registry.rs:341-364`](../../crates/multiview-cli/src/output_window_registry.rs#L341-L364)); it filters track packets only for ProgramMix, otherwise it sends all tracks ([`output_window_registry.rs:861-919`](../../crates/multiview-cli/src/output_window_registry.rs#L861-L919)). It is a subscription-window descriptor, not the physical mux stream-registration authority.

## 2. Proposed command, validation and refusal

Add a distinct output-track-set command; do not overload `AudioFeed::Track`, which selects one live routed feed on the output's program-audio slot. The request names one output and the complete desired selection: `program: bool`, an ordered set of declared `target_track` names, and the expected accepted output/audio-routing revision. It carries a caller operation ID and principal as existing output takes do. The complete-set form avoids ambiguous partial mutations and gives idempotent replay one stable body.

Validate off the output-clock path, against the accepted configuration and the currently opened run:

1. Authorize Read on every selected route input and Write on the output, following the existing two-ended output-take authorization (`routes/output_routing.rs:264-294`). Resolve each track name to exactly one `[audio].routes[].target_track`; reject unknown, duplicate, removed or renamed-stale tracks. The routing validator already rejects duplicate track names and unresolved source references (`audio.rs:201-268`; config cross-validation calls it in `lib.rs:1778-1802`).
2. Check the accepted output's `Output::audio_capability()` and actual run binding. The matrix exposes delivery (`Simultaneous`, `SelectOne`, `None`) and count capacity; config validation gates selection count (`schema.rs:3435-3477`, `audio.rs:420-454`). Do not infer live availability from transport capability alone. Refuse when the output is not in this run, has no relevant program/track packet binding, or the selected route is not opened.
3. Check the transport transition mode and required metadata. Current HLS and Cast represent selected tracks as alternate audio renditions (`schema.rs:2997-3005`; `pipeline.rs:15855-15878`); SRT carries selected streams as MPEG-TS PIDs (`sink.rs:1700-1710`, `sink.rs:220-248`); WebRTC emits only `StreamKind::Audio` and drops other kinds (`pipeline.rs:10585-10601`) and its output schema has one Opus m-line (`schema.rs:2757-2761`). Until each transport has an implemented commit adapter, refuse with a typed `transport-transition-unsupported` reason rather than returning accepted and silently keeping the old set.
4. Reserve one per-output operation and one bounded preparation slot. Typed refusals should distinguish `unknown-track`, `stale-revision`, `audio-capability`, `output-not-in-run`, `audio-not-open`, `transport-transition-unsupported`, `preparation-failed`, `capacity`, and `superseded`. These names are proposed wire values, not existing API values. Do not reserve idempotency state or output limiter capacity until authorization, shape, reference and capability checks pass; refund any reservation if the bounded enqueue fails.

The static matrix does not by itself settle operational transition support. It says HLS is SelectOne with unlimited declared renditions, SRT/RTSP are simultaneous, NDI has no selectable track, WebRTC has an AtMost(1) capability ([`schema.rs:3435-3477`](../../crates/multiview-config/src/schema.rs#L3435-L3477)). The running WebRTC path currently skips `apply_output_audio_selections` and consumes only program `Audio` packets; a one-track config is therefore not evidence that WebRTC currently switches track sets. Keep WebRTC refused for discrete-set changes until the output actually maps one selected clean track into its single Opus m-line or negotiates a supported replacement session.

## 3. Prepare and commit protocol

Use a bounded two-phase protocol. All name resolution, authorization, capability checks, allocations, mux metadata, prepared descriptors and muxer construction happen off the output clock. The control side submits one immutable `PreparedTrackSet` through a bounded `try_send`; at most one pending and one active generation are retained per output. A newer request may supersede a pending request, but must not grow a backlog.

The output clock does not wait for a sink. It publishes only a small generation/commit token at the output's next fresh tick after the transport adapter reports Ready. The audio packet/window dispatcher uses that same generation for the output binding, so packets before T are tagged with the old selection and packets from T onward with the new selection. A repeat tick does not commit; the proposal remains pending for a fresh output tick. If preparation is not Ready at the deadline or the output misses the staged generation, keep the old set and emit a typed refusal. This protocol must use bounded preallocated state, atomics or a fixed-capacity mailbox; no heap growth, lock, I/O, await, client acknowledgement or destruction of large old state on the clock.

For **HLS**, the legal transition boundary is a video keyframe / segment boundary. Close and publish the old segment using only the old registered PIDs. Open a new mux generation with its new stream registrations and header before writing packets of generation T. Publish the new media playlist/master rendition set atomically with the new generation; add `EXT-X-DISCONTINUITY` when the TS program/PID layout changes. Existing code already uses keyframes as segment boundaries (`sink.rs:3048-3062`) and has rolling playlists and separate per-track audio rendition playlists (`sink.rs:2518-2590`, `sink.rs:3538-3564`), but it does not rebuild the track-set topology at a normal GOP. A header already being written belongs wholly to the old generation: the sink actor finishes it with old packets, then transitions at a later eligible boundary; never mutate a stream table under that header.

For **SRT**, a discrete set is a set of MPEG-TS PIDs. A change can be player-visible only when a new PAT/PMT describes the new stream set. Do not change the registration under an open mux header. The candidate design is a new mux generation with an explicit PAT/PMT version at a transport packet boundary; preserve the SRT session if the mux API proves it can replace the program stream safely, otherwise classify the transition as reconnect-required and refuse a no-restart take. Receiver support for multiple PIDs varies; ADR-R005 calls this a delivery caveat, not a config capacity cap (`ADR-R005.md:10-14`). The implementation must test cooperating receivers and must not claim broad player interoperability from a sender-only test.

For **WebRTC**, an established SDP has one Opus m-line and the current runner forwards only the single `Audio` stream. Adding/removing an audio m-line mid-session requires renegotiation or a new session; the existing `EgressSink` packet path is not a renegotiation API. Therefore this proposal does not promise a dynamic WebRTC track list. Until a reviewed renegotiation mechanism exists, refuse any set mutation that changes the m-line topology with `transport-transition-unsupported`; a compatible single-track source switch may reuse the one Opus m-line only after implementation supplies the correct selected PCM/Opus feed.

For File, RTMP Push and any other single-container mux, a header is a session commitment. A new set cannot be applied in place. Require a distinct versioned output session/container boundary and an explicit restart/reconnect-class outcome unless a transport-specific packet-level table update is proven. The APIs must report this honestly rather than imply all transports have one transition rule.

## 4. Invariants #1 and #10

The encoder already produces the program and every declared track once, then each output binding selects packet indexes; `output_audio_tracks` is built once from the selected set (`pipeline.rs:3634-3676`). Preserve this encode-once path. A set change selects from already-running encoded tracks; it does not create per-output encoders or delay the Program clock.

The commit tick performs only a fixed-size generation swap and bounded descriptor lookup. The output sink actor owns mux headers, playlist writes, reconnects, packet filtering and cleanup. Each actor receives complete tick windows through existing bounded delivery; `OutputWindowRegistry::offer_complete` is off-clock, only enqueues to per-peer bounded queues, and rejects loss locally (`output_window_registry.rs:861-919`). Existing Push uses bounded client queues and drops/re-gates slow peers (`sink/push.rs:66-70,280-337`). Preparation or publication failure refuses/rolls back the output's set and may drop only that output's affected windows; it never blocks or removes a frame from another output or the Program clock.

The registry descriptor must add a selected track-set generation and ordered selected track identities to `EffectiveBinding`; `AudioDescriptor` remains the opened codec/time-base authority. On successful commit, publish the effective selection snapshot atomically for new subscribers, revoke stale-generation subscriptions or give them an explicit old-set end, and ensure the first window for a new generation contains only streams named by that generation. The existing `publish_effective` uses an atomic snapshot store and returns the generation (`output_window_registry.rs:646-662`); the present code intentionally retains peers whose binding identity is unchanged (`output_window_registry.rs:848-859`), so selection generation must be included in peer identity/validation rather than silently changing an existing peer's semantics.

## 5. Required clock-non-stall chaos test

Add a real engine/output integration test, not only a `PacketMuxSink` unit test:

1. Run a fixed-rate program with one HLS output and two named discrete AAC tracks. Capture every emitted output frame's sequential tick and PTS/DTS, plus output mux selection generation and HLS master/media playlists.
2. At a fixed future output tick T, submit a validated set replacing track A with track B. Inject a two-second delay into off-clock preparation and a second delay while the next segment's mux header/playlist is written. Hold the real sink actor; do not delay the output clock or fake the packet dispatcher.
3. Assert one valid frame per tick, contiguous tick-derived PTS/DTS and cadence within the existing threshold throughout both delays. Assert ticks <T use only generation A, ticks ≥T use only B, no segment header has a mixed PID/rendition table, and the HLS rendition list changes only at a segment boundary with the required discontinuity metadata. Assert program and unrelated outputs retain every frame.
4. Run a slow-consumer variant until the configured sink/window cap fills. Assert occupancy never exceeds that cap, the Program clock continues, and loss/refusal is attributed only to the affected output. Inject mux/header failure and assert old selection stays committed or a typed failure is visible; never report `applied` without the generation appearing in output readback.

The existing sink has test seams for header/packet/playlist failure and segments, but no prepared-set generation protocol; use its patterns rather than weakening existing tests (`sink.rs:2320-2335`, `sink.rs:2166-2180`, `sink.rs:3240-3368`).

## 6. Implementation reach and order

1. **API/control:** add a complete-set request, authorization, idempotency, plan/refusal vocabulary, operation outcome, and per-output readback (`crates/multiview-control/src/routes/output_routing.rs`, `output_routing.rs`, OpenAPI source). Keep transport-level `OutputAudioCapability` separate from live-run and transport-transition support.
2. **Tick/runtime:** carry selected set and generation in `RunOutput`, prepared bounded mailbox, and output-window selection; commit at one fresh output tick (`crates/multiview-cli/src/output_routing.rs`, `pipeline.rs`, `output_routing_control.rs`). Do not share mutable selection maps with the output clock.
3. **Binding and descriptor:** derive `output_audio_tracks` from the committed generation rather than once in pipeline build; include that set/generation in `EffectiveBinding`/`OutputWindowRegistry` and subscription validation (`pipeline.rs:3634-3676`, `output_window_registry.rs:132-207,646-662`). Existing API field `audio_tracks: All | ProgramMix` is insufficient for a selected-set subscription.
4. **Mux registration:** make `PacketMuxSink` consume generation-stamped complete windows. HLS needs per-generation mux registration at segment boundary, with master/media publication coordinated; SRT needs a verified PAT/PMT update or an honest reconnect refusal. `add_track_streams` registers streams only before the mux header (`sink.rs:220-248`, `2141-2178`, `3240-3368`).
5. **Transport coverage:** Cast has independent CMAF audio selection and metadata (`pipeline.rs:2057-2065,15855-15878`); WebRTC is mux-free and currently drops every packet kind other than Video/Audio (`pipeline.rs:10417-10420,10585-10601`). Each needs an explicit live capability decision; do not inherit HLS behavior by analogy.

## 7. Open panel questions / reversal triggers

- Is a bounded drop of the affected output during its mux-generation swap acceptable, or must each transport provide make-before-break with no output loss?
- Can libav's MPEG-TS muxer update PMT/PIDs on one SRT session without a new header/connection, and do required cooperating receivers honor it? If not, SRT's result is reconnect-required, not seamlessly live.
- For HLS, should an audio-set update publish a new master under the same URL with `EXT-X-DISCONTINUITY`, or a generation-scoped master URL? A client that cached the old master may not discover a new rendition without refresh/reload.
- WebRTC has one Opus m-line and the current path does not consume `slots.audio`; should config reject discrete selections until a source-to-Opus live path is built, or should a separate `audio:track` signal-selection feature be specified?

The design is reversible before implementation. The panel may reject live mutation of SRT or WebRTC and ship HLS-only first; report the capability per output/transport, never claim a universal live-switch flag.
