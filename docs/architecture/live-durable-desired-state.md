# Live desired-state durability: in-progress control-plane design

This isolated branch introduces `desired.json` as the authoritative, versioned, atomic envelope for accepted source, output, audio-routing, and layout intent. The envelope contains the full validated configuration, stable output API identities, the saved layout library, selected layout ID, and the exact selected layout body. `active.toml` remains an observational snapshot of commands adopted by the live engine; shutdown persistence must not overwrite accepted intent.

## Acknowledgement contract

For modeled runs, covered endpoints hold `lock_config_mutation`, check the resource precondition, compose and validate a prospective complete configuration, write a same-directory owner-only temporary file and fsync it, rename it to `desired.json`, and then change the resource store/ETag or send a command. A failed write returns a repository 5xx before any covered store or command mutation. Source live application is separate from durable acceptance: an accepted store edit can advertise `restart` when the live command is unavailable. Apply-layout reserves a bounded bus slot before committing the selected body, and only enqueues after a successful durable write. Output IDs are mapped to configuration positions in the envelope, not inferred from resource names after the first commit. On restart, a valid desired envelope outranks a stale `active.toml`; corrupt accepted intent fails startup instead of silently restoring older state. The saved library is restored from the authoritative envelope in both SQLite and default builds; a boot seed must never overwrite an existing SQLite layout ID.

## Single source of truth: every config collection commits through the envelope

Once `desired.json` exists it outranks `active.toml` on restart, so any collection that changed only its store would be silently reverted on restart, or by the next unrelated commit that rewrote the stale section (review H1, PR #190). The design is therefore **write-through, not fold-in**: every mutating route for a config-backed collection — sources, outputs, audio routing (with its output-selection propagation, committed under the accepted output identities), layouts, overlays, probes, devices, sync groups, salvos, tally profiles, source event automation rules, and the section families `iptv` and `graphics` (data sources, items, channels; with the `weather` mirror and the `/weather/locations` alias) — holds `lock_config_mutation`, checks its precondition, and calls `boot_model::commit_resource` (or `commit_desired*`) to atomically replace exactly that item in the full prospective configuration, validates the whole document, and only then projects the change into the store and the live engine. Composition never folds store state into the envelope, because a store projection that failed after a commit would then leak back in as accepted intent. A create of an id that already exists is refused before the durable write (`require_absent`), an edit replaces the item in place (preserving draw and recall order), and a delete removes it. The boot-file watcher commits the whole watched document through the same envelope before resyncing stores, and re-seeds the graphics hub from it. Section families have no store, so export, `active.toml` and revert read `graphics`, `weather` and `iptv` from the envelope; their per-resource versions (`iptv`, `graphics_data_sources`, `graphics_items`, `graphics_channels`) live in `resource_versions`, start at 1 for pre-envelope state, and strictly advance, so an A→B→A edit never returns an earlier `ETag`.

The envelope also carries a version and display name for every family. Overlays, probes, devices, sync groups, salvos and tally profiles are served from their stores, so each commit takes the higher of the envelope counter and the store version, and an accepted write to one of them always advances it. At startup `boot_model::restore_accepted_stores` rebuilds every config-backed store from the envelope, so names and `ETag`s continue across a restart and a pre-restart tag stays stale. The first commit imports bodies, names and versions from the existing stores. A store write that fails after the commit returns `CommitIndeterminate`, because the edit has already been accepted.

Known limit: a boot-file watcher resync bumps store versions for unchanged items without a matching envelope change. The next commit absorbs that difference, but a restart before it returns those items to their last committed version.

Graphics, IPTV, weather and events sections (later release branches) must follow the same rule when they land.

## Unfinished contract and release gate

Non-config runtime state (device runtime status, media-player transport, ephemeral cast sessions) is deliberately outside the transaction. SQLite layout writes remain a secondary projection that can fail after the envelope commits, leaving the immediate API response inconsistent until restart. No end-to-end production-host or release verification has occurred. In particular, do not merge or deploy this branch until a SQLite projection fault is handled, boot migration and rebind are tested, and independent review and CI pass.

## Isolation

All serialization, validation and disk writes run on the control plane; file I/O uses `spawn_blocking`. The engine never awaits a client or a disk write, and the existing fixed-cadence output loop is unchanged. A full command bus sheds at reservation, before a layout desired-state write.
