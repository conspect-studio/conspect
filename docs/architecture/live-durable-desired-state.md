# Live desired-state durability: in-progress control-plane design

This isolated branch introduces `desired.json` as the authoritative, versioned, atomic envelope for accepted source, output, audio-routing, and layout intent. The envelope contains the full validated configuration, stable output API identities, the saved layout library, selected layout ID, and the exact selected layout body. `active.toml` remains an observational snapshot of commands adopted by the live engine; shutdown persistence must not overwrite accepted intent.

## Acknowledgement contract

For modeled runs, covered endpoints hold `lock_config_mutation`, check the resource precondition, compose and validate a prospective complete configuration, write a same-directory owner-only temporary file and fsync it, rename it to `desired.json`, and then change the resource store/ETag or send a command. A failed write returns a repository 5xx before any covered store or command mutation. Source live application is separate from durable acceptance: an accepted store edit can advertise `restart` when the live command is unavailable. Apply-layout reserves a bounded bus slot before committing the selected body, and only enqueues after a successful durable write. Output IDs are mapped to configuration positions in the envelope, not inferred from resource names after the first commit. On restart, a valid desired envelope outranks a stale `active.toml`; corrupt accepted intent fails startup instead of silently restoring older state. The saved library is restored from the authoritative envelope in both SQLite and default builds; a boot seed must never overwrite an existing SQLite layout ID.

## Single source of truth: every config collection commits through the envelope

Once `desired.json` exists it outranks `active.toml` on restart, so any collection that changed only its store would be silently reverted on restart, or by the next unrelated commit that rewrote the stale section (review H1, PR #190). The design is therefore **write-through, not fold-in**: every mutating route for a config-backed collection — sources, outputs, audio routing, layouts, overlays, probes, devices, sync groups, salvos and tally profiles — holds `lock_config_mutation`, checks its precondition, and calls `boot_model::commit_resource` (or `commit_desired*`) to atomically replace exactly that item in the full prospective configuration, validates the whole document, and only then projects the change into the store and the live engine. Composition never folds store state into the envelope, because a store projection that failed after a commit would then leak back in as accepted intent. A create of an id that already exists is refused before the durable write (`require_absent`), an edit replaces the item in place (preserving draw and recall order), and a delete removes it. The boot-file watcher commits the whole watched document through the same envelope before resyncing stores.

The envelope also carries a version and display name for every family. Overlays, probes, devices, sync groups, salvos and tally profiles are served from their stores, so each commit takes the higher of the envelope counter and the store version, and an accepted write to one of them always advances it. At startup `boot_model::restore_accepted_stores` rebuilds every config-backed store from the envelope, so names and `ETag`s continue across a restart and a pre-restart tag stays stale. The first commit imports bodies, names and versions from the existing stores (see First-boot migration). A store write that fails after the commit returns `CommitIndeterminate`, because the edit has already been accepted.

A boot-file watcher resync writes a store only for an item whose content changed, and the file commit that precedes it advances the same item in the envelope. An unchanged item keeps its version, and a retried apply after a shed command moves nothing, because its commit finds equal bodies. A resync keeps a name set over REST unless the file changed that item's own `display_name`, in which case the envelope takes the new name too.

Known limits:

- A shed revert-to-start still commits Loaded to the envelope and then rolls the stores back to the pre-revert document. Until its retry completes, store-served families answer from a document the envelope no longer holds, and their versions can sit above the envelope's. The next commit absorbs that difference; a restart before it serves the envelope's Loaded state and its lower versions.
- Deleting a store-served item and creating it again restarts its store at version 1, while the envelope continues from the tombstoned counter. The served tag moves up to the envelope's counter at the next restart. Sources, outputs, audio and layouts are served from the envelope and do not have this gap.

Graphics, IPTV, weather and events sections (later release branches) must follow the same rule when they land.

## Layout projection faults

`desired.json` is the only truth for accepted layouts. `layouts.db` (or the in-memory repository) is a replaceable projection of it. Every layout read, precondition and working-document composition uses the envelope, so a failed projection write cannot change an API answer or an `ETag`, and no restart is needed.

After each commit, `layout_projection` reconciles the repository to the envelope, re-reading the envelope on every attempt so a stale attempt cannot undo a newer commit. A commit waits at most one second for its first attempt, so a stalled database cannot hold a response or the config-mutation lock longer than that. A failed attempt sets `layout_projection.degraded` on `GET /api/v1/config/boot-model`, logs at `error`, and the task makes up to five attempts per commit, with exponential backoff from 250 ms. A spent budget is reported as `degraded` with `retrying: false`. The next commit of any family, or the next boot, repairs the projection. `last_error` is withheld from scoped principals because a repository error can name any layout.

## First-boot migration

An existing install has `active.toml` and `layouts.db` and no `desired.json`. Boot serves that legacy state unchanged and writes nothing. Which document it starts from is still the `[control] start` policy: `resume` uses `active.toml`, and the default `boot` policy ignores it, so under `boot` the first commit accepts the boot file and the `active.toml` contents are not imported. `desired_migration` covers `resume`. The first commit creates the envelope from the document the run started from, not from a store composition: stores list id-sorted, which would reorder outputs against their positional identities, and a legacy working-layout row would replace the running canvas and cells. Bodies, names and versions are imported from the stores, so tags continue and a pre-migration tag is refused with `412`.

The selected layout rebinds to the saved definition that matches the running canvas, layout and cells, compared through their typed schemas because an authored body omits defaulted fields. If several saved definitions match, or none does, selection falls to the working layout entry, and that entry is added to the library when it is missing. A corrupt `desired.json` (unreadable, malformed, an unknown version or an inconsistent record) stops startup with an error naming the file and the reason, and the file is left untouched.

## Unfinished contract and release gate

Non-config runtime state (device runtime status, media-player transport, ephemeral cast sessions) is deliberately outside the transaction. The SQLite projection fault is handled and tested with a fault injected inside a real `layouts.db` (`layout_projection_fault`). Boot migration, rebind, restart identity, stale `If-Match` and corrupt-envelope refusal are tested through the real boot path, with a real `layouts.db` and a real socket, and the corrupt case through the real binary (`desired_migration`). CI runs these under `--features sqlite` on Ubuntu. They use small synthetic installs on the software path. Do not merge or deploy this branch until independent review and CI pass, and until the migration has been verified on a production host with a real install, because no end-to-end production-host or release verification has occurred.

## Isolation

All serialization, validation and disk writes run on the control plane; file I/O uses `spawn_blocking`. The engine never awaits a client or a disk write, and the existing fixed-cadence output loop is unchanged. A full command bus sheds at reservation, before a layout desired-state write.
