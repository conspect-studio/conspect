# REST audio route gain and mute — R3 design proposal (#105)

Status: **panel-reviewed design, not implemented**. The panel verdict and open blockers are recorded below. This note does not claim REST gain/mute works or that #105 is complete.

## Current boundary and failure

The REST `RouteTakeRequest` declares target/source and classifier hints, not gain/mute (`crates/multiview-control/src/routes/routing.rs:43-72`). `build_route_command` hardcodes `gain_db: 0.0, mute: false` for program-bus and discrete-track targets (`routing.rs:249-269`), although `Command::RouteAudio` already has both fields (`crates/multiview-control/src/command.rs:270-286`). The production command consumer ignores them with `..` (`crates/multiview-cli/src/control.rs:3005-3009`) and submits only `request_route(target, source, 480)` (`control.rs:4121-4137`). `AudioControlHandle` resolves the target/store off-clock and publishes a bounded repoint; its sole bake consumer applies repoints, then a separate latest gain table before the next audio tick (`crates/multiview-cli/src/audio.rs:709-739,792-866`). The engine `RouteApplier` also drops gain/mute (`crates/multiview-engine/src/route.rs:388-423`), but it is a distinct pure path: editing it alone cannot repair the live REST route. The configuration route already derives program-bus gain/mute through `AudioControlHandle::gains_for` (`cli/audio.rs:403-409,624-643`) and `pipeline::program_bus_gains_aliased` (`cli/pipeline.rs:22954-22983`); the regression at `cli/audio.rs:1201-1245` exercises it. Preserve its routing and mute semantics, while addressing the separate range-validation defect #590 below.

The issue's acceptance text is: “mixer tests: gain applied; mute silences without unrouting; unmute restores prior gain; REST take carries values.” A command-field assertion alone does not prove the mixer changes.

## Primary invariant: authored intent has explicit precedence

A REST gain/mute take is **durable authored operator intent**, not an ephemeral one-shot `pending_gains` publish. The existing `pending_gains` is one latest-wins table **derived from config**, and alias/config recomputation can replace it (`cli/audio.rs:624-643,834-865`). Publishing REST values into that table without a separate authored layer would silently erase the operator's choice at the next reload. Define per-route authored state keyed by authorized destination route identity, with independent optional authored gain and optional authored mute; keep it outside the render/clock path. Effective value resolution is **authored > config-derived > default** for each field. A REST request must explicitly distinguish absent (leave the current authored field unchanged), set (including explicit gain `0.0` dB or mute `false`) and reset (remove authored field, reveal current config-derived value). `0.0` dB is unity, not a reset. Default when neither layer provides a value: `0.0` dB and unmuted. Validate finite REST gain and reject values outside `[-96, 24]` dB with a typed error, without silently clamping a new API field. This is an **intentional asymmetry**, not parity with existing config: `multiview-config/src/audio.rs:120-122` and `routing.rs:588-590` validate finiteness only, while `cli/audio.rs:670` silently clamps finite values at use. A new fatal range check in `config.validate()` would prevent an existing `gain_db = 40.0` deployment from starting after upgrade (`cli/main.rs:2010-2013`); preserve config load availability and surface its substitution through the existing `config_warnings` advisory channel (#590). Making config fatal needs a separate migration path and is out of scope for #105. Persist authored state with accepted control intent across process restart; if persistence is unavailable, reject the REST take rather than return `applied=true` for a transient setting.

A config reload updates only the derived layer. Authored gain and mute survive it and continue to win; a reset made after reload reveals the **new** config-derived value. This must be visible in an authorized read/status surface with both authored and effective values before claiming operational completeness; a config reload may never silently overwrite an authored REST value. The panel chose a **separate append-only control-intent journal**, not a `DesiredState` extension or the debounced `active.toml` persister. `commit_desired_document` (`control/boot_model.rs:810`) delegates to `write_desired` (`boot_model.rs:288-328`), which serialises the entire `MultiviewConfig` and fsyncs it: at 100 Hz fader rate this would rewrite the full config every 10 ms. A debounced persister can lose a take already reported as `200` between its notify and its next flush. One small journal record is proposed to contain the operation ID, `Idempotency-Key`, destination, source, independently tri-state gain/mute and version; whether replay can safely reconstruct the authored layer before serving takes remains open pending persisted idempotency semantics. Correct acceptance order: **reserve idempotency key → `try_submit` → only if submitted, fsync ONE journal record → return `200`**. Journal-before-submit creates a phantom persisted take when command admission fails; a crash before fsync cannot claim `200`, and a crash after fsync but before response needs keyed idempotent replay. Failed fsync after command admission is **indeterminate**, not a false rollback: report the uncertain state, reconcile via a durable operation receipt, and do not acknowledge `applied=true` until the path is settled.

Mute is a **separate flag**, never stored as gain `0`. A mute applies effective zero to the program-bus strip while retaining its route, authored gain and discrete track. Unmute restores the effective gain resolved by authored > config > default; if config changed during mute, authored gain still wins, otherwise the new config gain wins. The clean discrete track's bytes and source selection do not change when only the program-bus mute changes. For a discrete-track `RouteAudio` take, the control contract must define whether gain/mute applies to the named track or only the program-bus contribution; refuse unsupported combinations instead of reporting successful application of ignored fields. Do not promise a separately attenuated discrete track without an explicit output-path design.

## Admission, tick ordering and crossfade interaction

Authorize both source and destination before reserving an idempotency key (`routing.rs:179-185`). Parse/validate gain/mute and reset in the REST handler, reserve the idempotency key, admit the whole route intent with `try_submit`, then fsync the journal record before acknowledging `200` (or return a typed `202 durability-pending` when measured fsync latency makes synchronous durability unsuitable). Submission alone is not physical bake completion: never claim `applied=true` before the bus observes it (#588). The control-side producer must resolve target/store and publish one bounded latest-intent record that carries route, authored gain and mute together. If the bounded mailbox is full, refuse visibly (`503`/typed refusal); do not grow, block, or drop an accepted intent silently. Coalescing by destination must keep its latest *whole* intent, not pair the last source with an earlier gain. Prepare conversion from dB to linear and all `Arc`/map allocation off-clock. This design must be reconciled with the existing cap of 256 pending repoints (`cli/audio.rs:133-140,729-739`), the one-slot config `pending_gains` table, and concurrent alias/config changes before implementation.

The sole bake consumer applies bounded membership updates, then repoints, then effective gain/mute before producing the **next audio tick** (`cli/audio.rs:792-866`). The authored apply stays **inside the existing `channels.read()` scope** (`audio.rs:849-864`): zero new locks on the output path, and no new `channels.write()` (the pre-existing lock contention remains #589). It must not await a client or hold an HTTP lock, and it must not allocate a growing queue on the output clock. Program output emits one valid, correctly-stamped frame each tick independent of the control operation (invariants #1 and #10). Existing `ProgramBus::set_program_gain_ramped` performs a bounded per-sample ramp from current effective gain (`crates/multiview-audio/src/program.rs:287-334`); the discrete track remains a clean independent feed.

`ProgramBus::repoint_crossfade` captures the channel's **current** gain for its outgoing strip, then crossfades an incoming strip (`program.rs:233-284`). A REST gain change while that crossfade is active must apply to the **incoming** strip only after the crossfade completes. Today's `apply_pending` processes repoints then gains in the same bake (`cli/audio.rs:821-865`); calling `set_program_gain_ramped` there immediately replaces the incoming up-ramp from its current effective position (`program.rs:312-333`). The implementation must add generation-aware deferral rather than assume the existing ordering already meets the proposal. The outgoing strip finishes at its captured level; the authored value remains durable during the flight, and the next bounded bake step starts the new gain ramp on the incoming route. This avoids abruptly changing a dying strip or doubling a new gain on both. The panel chose a bake-owned **fixed-array completion ring** inside `ProgramBus`: `[(RoutePoint, u64); N]`, where `N` bounds concurrent crossfades. `repoint_crossfade` mints the flight generation; `retire_completed_fades` writes its tagged completion at actual outgoing-strip retirement (`program.rs:527-544`); `apply_pending` drains it before the next mix and ignores stale generations. A ready-bit variant adds an indirection to the same ring; a lock-free queue adds contention machinery where none exists, because retirement and `apply_pending` run on the same bake thread (`pipeline.rs:9131`). Preallocate ring storage; refuse or report capacity instead of growth or overwrite. A second route or config reload during the flight must supersede by generation and never apply an old value to a newer source. **Blocking panel finding:** a switcher AUTO calls `crossfade_program_source` (`pipeline.rs:9138` → `audio.rs:905-924`); its `gain_of` resolves via `gains_for` → `program_bus_gains_aliased` (`pipeline.rs:22954-22983`), reading only config `AudioRoute.gain_db` at `:22978`. That silently clobbers an authored gain on the mixer for the whole dissolve ramp, and again on every new dissolve. Resolve **authored > config** in that path too; correcting only `apply_pending` is insufficient. Include a second dissolve starting while the prior flight completes in the chaos proof.

## Required verification before implementation approval

1. REST integration: submit nonzero `gain_db` for an authorized bus destination, drain the **real CLI audio bake consumer**, and assert the actual `ProgramBus::program_gain` at its route point (not merely the submitted command). Assert a scoped principal cannot address a foreign source or target. Validate malformed, NaN, infinite and out-of-range REST values fail before idempotency reservation; the separate config path remains finite-only and must emit a visible clamp advisory (#590), not fail startup.
2. Mute/unmute: route a named discrete track and program-bus source, capture the clean discrete track before/after mute, and assert identical source/bytes while program bus is silent. Unmute must restore the previous authored gain; test a config reload while muted, then reset to reveal its new derived gain. A rejected unsupported discrete-track gain/mute must return a typed refusal, not success.
3. Real-path R3 chaos: drive the actual program output clock under sustained gain/mute/route changes and a stalled control consumer. Capture every emitted tick and PTS/DTS and assert exactly one valid frame per tick, no gap/drop/repeated or unstamped output caused by REST changes. Assert finite queue occupancy never exceeds the specified cap and admission failures are observable. Inject a gain change **mid-repoint**, an alias/config reload, and two overlapping AUTO dissolves; prove incoming-only post-crossfade resolution, authored>config gain in `crossfade_program_source`, and stale-generation rejection. Include a deliberately blocking/allocating mutant or negative control that the cadence assertion detects. Do not loosen existing timing/test bounds.
4. Contract parity: `RouteTakeRequest` JSON, generated OpenAPI and generated web TS types must declare the same optional set/reset semantics that the live consumer honors. The existing config path's gain/mute regression must remain green.
5. R3 implementation review: evaluate authored-state durability and crash ordering, bounded bake work, crossfade generation, discrete-track semantics, and actual clock proof. The panel verdict below approves only the design direction, not an implementation or production deployment. Do not ship until unresolved blockers are answered.

## Panel decision, dissent and unresolved work

The author is `gate` (OpenAI). Blind seats: `gpt-6.2-astra` (OpenAI), `google/gemini-3.1-pro-preview` (Google), and `mistralai/mistral-large-4-1t-a52b` (Mistral AI). Fresh reviewer: `deepseek/deepseek-v4-pro` (DeepSeek). All retain authored > config > default, mute as a separate flag, visible capacity refusal, config-only `pending_gains` and preallocated bake-owned completion. This is multi-vendor coverage but **not the named panel pair**: `claude-fable-5-2` (Anthropic Fable 5.2) was specifically requested and unavailable (`SUBSCRIPTION_ONLY_ROUTING_EXHAUSTED` on every Anthropic route; one retry spent). xAI and Z.ai routes were also exhausted and Moonshot timed out. Record this reduced named-vendor independence as a limit of the verdict, not as implementation approval. The source panel record was session-local scratch, verified SHA-256 `6f96151cadb46cdd9626671d83cb108274ef81e4ac064d71c6f9cc002ae7aa88`; this note embeds the durable decision and does not depend on that scratch file.

**Resolved persistence dissent:** Astra proposed extending `DesiredState`; Mistral proposed a separate append-only journal but originally fsync-before-submit; Gemini proposed a small ledger with fsync-before-memory-publish. DeepSeek rejected the whole-config `DesiredState` rewrite at fader rate and the debounced `active.toml` gap, selected the separate journal, and corrected ordering to reserve → `try_submit` → fsync one record → `200` to avoid phantom takes on replay. **Resolved completion dissent:** Astra's ready-bit retirement is a ring with an extra step; Gemini's lock-free queue solves nonexistent inter-thread contention; Mistral's fixed-array ring is the chosen single-owner mechanism. The reviewer additionally identified the blocking `crossfade_program_source` authored-gain clobber above; #588 tracks silent oldest-intent drop plus false `applied: true`, and #589 tracks pre-existing output-path lock contention.

**Still open, not silently solved:** (1) the journal must persist the `Idempotency-Key` because the current idempotency store is in-memory (`routes/mod.rs:622`); replay without keys can double-submit, and fsync failure after `try_submit` needs an honest indeterminate receipt. (2) A new dissolve beginning as an older crossfade retires can reintroduce config gain, even after the first path is fixed; generation-tagged overlap proof is mandatory. (3) Per-take journal fsync latency at ~100 Hz is unmeasured; if too slow, return a typed `202 durability-pending` with observable completion instead of transient `200`. The panel's disproof conditions are a genuinely field-only `DesiredState` commit, proof the switcher crossfade never runs after authored gain, or measured journal fsync within the fader interval. None is established here.

Decline publishing a REST one-off into `pending_gains`: later config/alias recomputation silently undoes it. Decline encoding mute as zero *authored* gain: unmute cannot recover the intended level. Decline changing only engine `RouteApplier`: the deployed CLI-owned bus never reads it. Revisit the authored layer if durable operation/journal ordering or the real-clock chaos proof fails; split persistence from live application rather than return a falsely successful take.
