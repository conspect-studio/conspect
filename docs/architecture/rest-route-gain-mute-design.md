# REST audio route gain and mute — R3 design proposal (#105)

Status: **proposal, not implemented**. A design panel must resolve the clock-path and ownership questions below before code is changed. This note does not claim that REST gain/mute works or that #105 is complete.

## Current boundary and failure

The REST `RouteTakeRequest` declares target/source and classifier hints, not gain/mute (`crates/multiview-control/src/routes/routing.rs:43-72`). `build_route_command` hardcodes `gain_db: 0.0, mute: false` for program-bus and discrete-track targets (`routing.rs:249-269`), although `Command::RouteAudio` already has both fields (`crates/multiview-control/src/command.rs:270-286`). The production command consumer ignores them with `..` (`crates/multiview-cli/src/control.rs:3005-3009`) and submits only `request_route(target, source, 480)` (`control.rs:4121-4137`). `AudioControlHandle` resolves the target/store off-clock and publishes a bounded repoint; its sole bake consumer applies repoints, then a separate latest gain table before the next audio tick (`crates/multiview-cli/src/audio.rs:709-739,792-866`). The engine `RouteApplier` also drops gain/mute (`crates/multiview-engine/src/route.rs:388-423`), but it is a distinct pure path: editing it alone cannot repair the live REST route. The configuration route already derives gain/mute and works (`cli/audio.rs:655-670,1201-1245`); preserve that path.

The issue's acceptance text is: “mixer tests: gain applied; mute silences without unrouting; unmute restores prior gain; REST take carries values.” A command-field assertion alone does not prove the mixer changes.

## Primary invariant: authored intent has explicit precedence

A REST gain/mute take is **durable authored operator intent**, not an ephemeral one-shot `pending_gains` publish. The existing `pending_gains` is one latest-wins table **derived from config**, and alias/config recomputation can replace it (`cli/audio.rs:624-643,834-865`). Publishing REST values into that table without a separate authored layer would silently erase the operator's choice at the next reload. Define per-route authored state keyed by authorized destination route identity, with independent optional authored gain and optional authored mute; keep it outside the render/clock path. Effective value resolution is **authored > config-derived > default** for each field. A REST request must explicitly distinguish absent (leave the current authored field unchanged), set (including explicit gain `0.0` dB or mute `false`) and reset (remove authored field, reveal current config-derived value). `0.0` dB is unity, not a reset. Default when neither layer provides a value: `0.0` dB and unmuted. Validate finite bounded gain before accepting; apply the same `[-96,24]` dB range as existing config rather than silently clamp an out-of-range REST value. Persist authored state with accepted control intent across process restart; if persistence is unavailable, reject the REST take rather than return `applied=true` for a transient setting.

A config reload updates only the derived layer. Authored gain and mute survive it and continue to win; a reset made after reload reveals the **new** config-derived value. This must be visible in an authorized read/status surface with both authored and effective values before claiming operational completeness; a config reload may never silently overwrite an authored REST value. No new REST persistence mechanism is chosen merely by this note: the panel must decide its key/transaction and crash ordering against the accepted configuration repository.

Mute is a **separate flag**, never stored as gain `0`. A mute applies effective zero to the program-bus strip while retaining its route, authored gain and discrete track. Unmute restores the effective gain resolved by authored > config > default; if config changed during mute, authored gain still wins, otherwise the new config gain wins. The clean discrete track's bytes and source selection do not change when only the program-bus mute changes. For a discrete-track `RouteAudio` take, the control contract must define whether gain/mute applies to the named track or only the program-bus contribution; refuse unsupported combinations instead of reporting successful application of ignored fields. Do not promise a separately attenuated discrete track without an explicit output-path design.

## Admission, tick ordering and crossfade interaction

Authorize both source and destination before reserving an idempotency key (`routing.rs:179-185`). Parse/validate gain/mute and the reset operation in the REST handler, then atomically persist the authored change with the accepted route operation before returning success. The control-side producer must resolve target/store and publish one bounded latest-intent record that carries route, authored gain and mute together. If the bounded mailbox is full, refuse visibly (`503`/typed refusal); do not grow, block, or drop an accepted intent silently. Coalescing by destination must keep its latest *whole* intent, not pair the last source with an earlier gain. Prepare conversion from dB to linear and all `Arc`/map allocation off-clock. This design must be reconciled with the existing cap of 256 pending repoints (`cli/audio.rs:133-140,729-739`), the one-slot config `pending_gains` table, and concurrent alias/config changes before implementation.

The sole bake consumer applies bounded membership updates, then repoints, then effective gain/mute before producing the **next audio tick** (`cli/audio.rs:792-866`). It must not await a client or hold an HTTP lock, and it must not allocate a growing queue on the output clock. Program output emits one valid, correctly-stamped frame each tick independent of the control operation (invariants #1 and #10). Existing `ProgramBus::set_program_gain_ramped` performs a bounded per-sample ramp from current effective gain (`crates/multiview-audio/src/program.rs:287-334`); the discrete track remains a clean independent feed.

`ProgramBus::repoint_crossfade` captures the channel's **current** gain for its outgoing strip, then crossfades an incoming strip (`program.rs:233-284`). A REST gain change while that crossfade is active must apply to the **incoming** strip only after the crossfade completes. The outgoing strip finishes at its captured level; the authored value remains durable during the flight, and the next bounded bake step starts the new gain ramp on the incoming route. This avoids abruptly changing a dying strip or doubling a new gain on both. The panel must settle how completion is observed on the bake owner without polling or allocation on the output clock. A second route or config reload during the flight must supersede by generation and never apply an old value to a newer source.

## Required verification before implementation approval

1. REST integration: submit nonzero `gain_db` for an authorized bus destination, drain the **real CLI audio bake consumer**, and assert the actual `ProgramBus::program_gain` at its route point (not merely the submitted command). Assert a scoped principal cannot address a foreign source or target. Validate malformed, NaN, infinite and out-of-range values fail before idempotency reservation.
2. Mute/unmute: route a named discrete track and program-bus source, capture the clean discrete track before/after mute, and assert identical source/bytes while program bus is silent. Unmute must restore the previous authored gain; test a config reload while muted, then reset to reveal its new derived gain. A rejected unsupported discrete-track gain/mute must return a typed refusal, not success.
3. Real-path R3 chaos: drive the actual program output clock under sustained gain/mute/route changes and a stalled control consumer. Capture every emitted tick and PTS/DTS and assert exactly one valid frame per tick, no gap/drop/repeated or unstamped output caused by REST changes. Assert finite queue occupancy never exceeds the specified cap and admission failures are observable. Inject a gain change **mid-repoint** and an alias/config reload, prove incoming-only post-crossfade resolution and stale-generation rejection. Include a deliberately blocking/allocating mutant or negative control that the cadence assertion detects. Do not loosen existing timing/test bounds.
4. Contract parity: `RouteTakeRequest` JSON, generated OpenAPI and generated web TS types must declare the same optional set/reset semantics that the live consumer honors. The existing config path's gain/mute regression must remain green.
5. R3 panel and independent review: evaluate authored-state durability and crash ordering, bounded bake work, crossfade generation, discrete-track semantics, and actual clock proof. OpenAI seats may be used while Anthropic/xAI routes are exhausted, but such a panel has **reduced vendor independence**; record actual model/vendor IDs and dissent instead of calling it cross-vendor by implication. Do not ship implementation until unresolved blockers are answered.

## Alternative declined and reversal trigger

Decline publishing a REST one-off into `pending_gains`: it is derived from config and later recomputation would silently undo accepted intent. Decline encoding mute as zero gain: unmute cannot recover the authored gain. Decline changing only engine `RouteApplier`: the deployed CLI-owned bus never reads it. Revisit the proposed authored layer if a durable control repository cannot atomically pair the route and setting, or if the real-clock chaos test shows any missed tick, lock wait or unbounded allocation. In that case split persistence and live application further; do not return an apparently successful REST take.
