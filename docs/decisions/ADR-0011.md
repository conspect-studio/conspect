# ADR-0011: Cross-platform targets: Linux containers (NVIDIA + VAAPI), macOS native, Windows native

- **Status:** Proposed
- **Area:** Core Engine
- **Date:** 2026-06-02 (amended 2026-11-10: Windows added)
- **Source brief:** [core-engine.md](../research/core-engine.md)

## Decision

Ship Linux as multi-stage containers (an NVIDIA/CUDA variant relying on the NVIDIA Container Toolkit driver injection with NVIDIA_DRIVER_CAPABILITIES including video, and a generic/VAAPI variant via /dev/dri passthrough) and macOS as a native, signed+notarized universal2 (aarch64+x86_64) binary with inside-out-signed bundled dylibs, and **Windows (x86_64) as a native, Authenticode-signed binary** with its pinned LGPL FFmpeg DLLs shipped beside it.

## Rationale

macOS GPU (VideoToolbox/Metal) cannot run in containers, so macOS must be native. The toolkit injects host driver libs so images stay lean and driver-agnostic, but video capability is mandatory or NVENC/NVDEC silently vanish. universal2 covers Apple Silicon + Intel Macs in one artifact.

## Alternatives considered

Single mega-image with everything (rejected: bloat, conflated driver requirements). Per-arch macOS binaries (rejected: worse UX vs universal2). Docker on macOS for GPU (rejected: impossible — Linux VM, no Metal).

## Consequences

Startup must probe HW (dlopen + throwaway sessions) and fail loudly / fall back to VAAPI/CPU; pin SDK->driver minimum (e.g. SDK 13.0 -> driver >=570). VAAPI needs dynamic render/video GID resolution. macOS needs hardened-runtime + consistent Team ID + @rpath install names + notarytool/stapler; libavformat DNS must be watchdogged.

## Amendment (2026-11-10): Windows is a supported native target

The original decision excluded Windows. The product owner reversed that: Windows is in scope.

- **Shape:** native `x86_64-pc-windows-msvc` binary (no container: like macOS, the GPU and local
  capture paths are not reachable from a container), built with the MSVC toolchain.
- **FFmpeg:** our pinned LGPL 9.x (ADR-0031) built from the same verified source and allowlist
  as the other platforms, with a Windows hardware profile (NVENC/NVDEC via `nv-codec-headers`,
  D3D11VA decode, Media Foundation where it adds value). Third-party Windows FFmpeg builds
  (gyan, BtbN, Chocolatey) are never linked — they are GPL or carry a different allowlist.
- **Packaging:** the libav DLLs ship next to the executable with the LGPL/GPL licence texts
  (the release-archive rule from ADR-0031); Authenticode signing when the signing secret is
  present.
- **Local devices:** Media Foundation for cameras and WASAPI for audio in/out, behind
  off-by-default features and the same bounded latest-slot / audio-servo seams as the macOS
  AVFoundation/CoreAudio work (invariants #1/#10 apply unchanged).
- **CI:** a `windows-latest` check/test leg plus a pinned-FFmpeg leg, mirroring the macOS job.
- **Privacy:** Windows camera/microphone consent is per-app and per-session; a process started
  from a non-interactive session may be denied, so hardware tests run in the interactive
  desktop session (as the macOS tests run via a GUI-session launcher).
