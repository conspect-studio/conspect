# ADR-0101: Web site templates — declarative site definitions, Windy first, operator acceptance of site terms

- **Status:** Proposed
- **Area:** Input / Web / Guardrails
- **Date:** 2026-11-07
- **Source:** operator request; spike results
- **Builds on:** [ADR-0102](ADR-0102.md), [ADR-0100](ADR-0100.md)

## Context

A site needs login, view selection, a clean picture and proof the picture is correct. These differ per site and break when the site changes, so they must not spread through engine code.

Windy facts (2026-11-07):

- Login is an in-page form (`#email`, `#password`, `#submitLogin`), with no captcha or 2FA seen. One cookie, `_account_sid` on `.windy.com`, lasts about 400 days. A persisted profile and cookie re-injection both restored Premium. Session state does not reach `embed.windy.com`.
- URL carries overlay, position and zoom. Timeline and play state are not in the URL.
- Satellite and Wind on the main site need login. The embed needs none but has no Premium layers.
- Radar needs WebGL. Without it, the page silently falls back to the Wind overlay.
- The radar WebGL canvas paints its own opaque grey, so Windy radar cannot be transparent through CSS.
- At widths below about 960 px the site switches to a mobile layout with different selectors.
- `W.store.get('overlay')` reported the active overlay on the embed. Timeline clicks work only as real mouse events.

Windy terms of use (effective 1 Sept 2023, read 2026-11-07): §8.5.1 excludes the radar overlay from the screenshot and video permission. §4.6 prohibits automated access, circumventing or blocking advertisements, and giving credentials to another person. §3.1.2 limits free services to private persons. §8.6.3 covers the embed widget and requires its logo.

## Decision

1. **A template is data plus a small script.** It lives in `multiview-webengine/templates/<id>/` as a versioned manifest with: allowed hosts, parameter schema, URL builder, login steps, session health check, page-ready check, hide-CSS, capture method per overlay, timeline stepping script, and validators. Engine code holds no site selectors.

2. **Templates are built in for now.** Operator-authored templates are a later decision, because a template runs script in a logged-in page.

3. **Windy template.** Parameters: overlay (`radar`, `satellite`, `wind`, others as validated), lat, lon, zoom, width, height, and loop range. Width must be at least 1024 so that the desktop layout applies. Logged-in main site is the default. The embed is an explicit no-login option.

4. **Session handling.** A single profile per site account is shared by sequential jobs, so a capture does not log in again. Login runs only when the health check fails. Login attempts are limited (default 2 per hour per account), then the job fails and raises a warning, so a bad password cannot lock the account. A captcha or 2FA fails the job with a named reason; the engine never tries to bypass it.

5. **Validators, all required for acceptance.** Overlay active as requested; logged-in state as required; no "No data!" text; no UI selector visible during capture; expected frame count within tolerance; picture not uniform. Radar frames carry no colour test, because a dry day has no echoes.

6. **Clean picture.** The template hides UI, logo and attribution in the capture. Attribution at broadcast is the operator's responsibility through the CG, and the slot metadata carries a default attribution string.

7. **Site terms: user acceptance.** The template setup page shows the site's terms link and a required checkbox. The API refuses to save or run a Windy fill without `terms_accepted`. Stored fields: user, time, template id, template terms version. If the template's terms version changes, acceptance is needed again before the next run. The text states that the user is responsible for having rights to capture and broadcast the content.

8. **Failure feedback.** A template failure names the failed step and validator. The last failed screenshot is kept per fill, mode 0600, with logged-in account regions excluded from any support bundle.

## Rationale

Keeping selectors in one manifest confines site breakage to one file and one test. Strict validators convert the most likely failure, a plausible wrong picture, into a visible job failure. Recording acceptance puts the terms decision where the operator decided it should sit.

## Alternatives considered

| Alternative | Rejected because |
| ----------- | ---------------- |
| Windy Map Forecast API | Terms bar redistribution, and radar was not confirmed in the layer list. |
| Embed as the default | Operator requires logged-in access to Premium layers. |
| Operator-supplied scripts in v1 | Untrusted script inside a logged-in page needs its own security review. |
| A global terms setting | Acceptance must name the template and the user. |
| Colour check for radar echoes | Fails on a dry day. |

## Consequences

- **Terms risk stays real.** The checkbox records who accepted; it does not create permission. On our reading, broadcast of a captured radar overlay is outside §8.5.1 and an automated login falls under §4.6, and hiding the logo may conflict with widget and advertising terms. An account could be suspended. This ADR records the operator's decision and is not legal advice. Written permission from Windy remains the safer path.
- Windy can change its site at any time. A nightly template check should run where credentials exist, and Windy failures should not block CI.
- The account is shared by all jobs on a host; §4.6 restricts sharing credentials with another person, so each operator organisation supplies its own account.
- Fallback templates (RainViewer, BOM) carry their own licence limits and are not in scope here.
