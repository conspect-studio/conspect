# ADR-0105: macOS GPU compositing runs on wgpu's Metal backend; a native IOSurface path is deferred

- **Status:** Accepted
- **Area:** Core engine / Compositor (multiview-compositor), macOS
- **Date:** 2026-11-11
- **Source:** product-owner decision for macOS support; measurements on an Apple-Silicon test host
- **Builds on:** [ADR-0004](ADR-0004.md) (zero-copy islands), [ADR-0005](ADR-0005.md) (custom GPU compositor), [ADR-0011](ADR-0011.md) (macOS native target)
- **Refines:** ADR-0005's `MetalCompositor` and [hardware-and-efficiency §4](../architecture/hardware-and-efficiency.md): the first macOS GPU compositor is the existing wgpu compositor on wgpu's Metal backend, not a separate native Metal implementation.

## Context

ADR-0005 planned three compositor backends (CUDA, Metal, Vulkan/wgpu). The docs said that wgpu's
Metal backend "cannot do NV12", so macOS needed a native Metal compute compositor fed by IOSurface
through `CVMetalTextureCache`. This is true for a *native* NV12 (biplanar) texture format, but the
wgpu compositor never uses one. It uploads NV12 as two plain textures (`r8unorm` Y and `rg8unorm`
UV) and writes NV12 output through write-only storage textures of the same formats
(`gpu/device.rs::supports_nv12_storage_writes`). Metal supports all of these.

The facts measured on an Apple-Silicon test host (M3 Ultra, macOS 26) at main 4077a47c:

- The wgpu GPU suites (`gpu_compositor`, `nv12_alpha_gpu`, `gpu_surface_pool`,
  `overlay_gpu_subpass`, `--features wgpu,overlay`) select a Metal adapter and pass with no
  no-adapter skip.
- `alpha_composite_bench` (1920x1080, 9 tiles of 640x360, 120 iterations, release, including upload
  and readback): GPU median 1.60 / 1.77 / 2.07 ms (p95 1.78 / 2.62 / 2.24 ms) for 0 / 1 / 6 alpha
  tiles, against CPU median 7.05 / 7.16 / 6.94 ms. GPU-to-CPU fallbacks: 0.
- The 25 fps tick budget is 40 ms. The GPU path uses about 5 % of it.

On main the `apple` preset does not enable the cli `gpu` feature, so macOS composites on the CPU;
#244 adds `gpu` to the preset. The compositor feature `metal` was an empty placeholder.

The VideoToolbox decoder and encoder in this repo exchange frames in host memory: decode
downloads to NV12 (`hwdecode.rs`), and the VT encoder takes NV12 frames
(`codec.rs::videotoolbox_encoder`). The VT → Metal → VT zero-copy island of ADR-0004 does not
exist yet on any path.

## Decision

macOS GPU compositing uses the existing wgpu compositor on wgpu's Metal backend. The `apple`
preset enables the cli `gpu` feature (#244). The run-time backend selection and the CPU fallback are the
same as on Linux. There is one compositor code path and one set of WGSL shaders for Linux
(Vulkan/GLES) and macOS (Metal).

- `multiview-compositor/metal` stays a reserved, empty feature name. It does not select anything,
  and no code may depend on it until a native path exists.
- The docs no longer say that macOS needs native Metal because wgpu cannot do NV12. They say that
  wgpu on Metal is the macOS compositor, and that a zero-copy IOSurface path is a future
  optimisation.
- A native IOSurface / `CVMetalTextureCache` path (VT decode → Metal → VT encode, no host copy) is
  deferred. It is reopened only when a measured macOS workload is bound by the host copies
  (upload + readback, or VT download/upload) and not by the composite itself. It would be a new
  backend behind the same `Compositor` seam, gated by the `metal` feature, with unsafe FFI in a
  leaf crate (data-plane-safety rules).

## Rationale

- **Measured, not assumed:** the portable path already runs on Metal, is correct (the parity
  suites pass), and its composite takes about 2 ms of a 40 ms tick on the target class of hardware.
- **One shader set:** a second compositor for one platform doubles the colour-pipeline surface
  (fixed colour order, range handled once in-shader) that must stay bit-consistent across
  backends. Every shader fix would need to be done twice.
- **Zero-copy needs more than a compositor:** VT decode and encode use host memory here. A native
  Metal compositor by itself removes no copies. The island needs `AVHWFramesContext` on
  VideoToolbox, `CVPixelBuffer` ↔ `MTLTexture` interop, IOSurface use-count lifetimes, and a VT
  encoder that accepts `CVPixelBuffer` input. That is a separate and larger work item.
- **Safety:** the wgpu path needs no new `unsafe`. A native path needs Objective-C/Metal FFI.

## Alternatives considered

| Alternative | Rejected because |
| ----------- | ---------------- |
| Native Metal compute compositor now (ADR-0005 `MetalCompositor`) | It removes no copy while VT decode and encode are host-memory. It duplicates the WGSL colour pipeline in MSL. It adds Objective-C FFI. The measured composite cost (≈2 ms / 40 ms) leaves nothing to gain today. |
| wgpu with a native NV12 texture (`TextureFormat::NV12`) | It is not needed: the R8 + RG8 plane upload already works on every backend. The native format is not supported on wgpu-Metal, so it would also make macOS different from Linux. |
| Keep macOS on the CPU compositor | The CPU path takes 7 ms per 9-tile 1080p composite against the GPU's 1.6 ms, and it competes with decode and encode for CPU cores. |
| Remove the `metal` feature name | Presets and downstream configs already list it. Keeping it reserved and documented as empty is cheaper than a breaking rename, and the name is right for the future native path. |

## Consequences

- macOS and Linux share the GPU compositor and its parity tests. The macOS pinned-FFmpeg CI leg (#244)
  clippy-checks the `gpu` preset. GPU execution parity on Metal is verified on hardware, not on
  hosted runners (they may not expose a usable Metal adapter; the suites then take the
  documented no-adapter skip).
- macOS pays two host copies per tile (upload and readback) plus the VT download/upload. This is
  the documented cost of ADR-0004's "one explicit copy at a boundary" model until the IOSurface
  island exists.
- Invariants #1 and #10 are unchanged: the compositor runs on the same tick-driven path. A genuine GPU
  failure on Metal takes the same per-frame CPU fallback (`backend.rs`) as on Vulkan.
- The reopen criterion for the native path is a measured copy-bound macOS workload, recorded in a
  new ADR that supersedes the deferral part of this one.
