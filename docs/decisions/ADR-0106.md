# ADR-0106: Local audio devices (CoreAudio, WASAPI) through cpal, isolated by lock-free rings and the existing audio servo

- **Status:** Proposed
- **Area:** Resilience & A/V / Local devices
- **Date:** 2026-11-11
- **Source:** product-owner request for macOS and Windows hardware support; issue #276
- **Builds on:** [ADR-0011](ADR-0011.md) (macOS + Windows native), [ADR-0044](ADR-0044.md) §5 (display audio: FIFO + servo + adaptive resampler), ADR-R005 (audio store, gap-free reads), [ADR-0033](ADR-0033.md) (AES67: an audio-only source)
- **Design note:** [local-audio-devices.md](../architecture/local-audio-devices.md)

## Context

Conspect has no way to use a local microphone, line input or audio interface as a source, and no way
to play program audio to a local output, except ALSA HDMI on a KMS display head (ADR-0044 §5). The
macOS and Windows targets (ADR-0011) need both. FFmpeg's `avfoundation`/`dshow` input devices can
capture audio, but they deliver it on FFmpeg's demux thread with no device-clock information, and
FFmpeg has no matching output device on either platform.

A device callback runs on an OS real-time thread, and the device sample clock is a separate crystal
from the output clock. A wrong design here breaks invariant #1 (output clock never blocks) or #10
(the engine never waits on a peer), so this is class R3.

## Decision

Add an off-by-default `audio-device` feature backed by [`cpal`](https://crates.io/crates/cpal)
(Apache-2.0; CoreAudio on macOS, WASAPI on Windows) in a new leaf crate `multiview-audio-device`
(`#![forbid(unsafe_code)]`; all FFI stays inside cpal).

1. **Input source** `kind = "audio_device"` (audio-only, like AES67: no tile, no video store).
   - The cpal input callback only converts the device samples to interleaved `f32` and pushes them
     into a preallocated wait-free SPSC ring ([`rtrb`](https://crates.io/crates/rtrb), MIT/Apache).
     No lock, no allocation, no syscall. A full ring drops the new samples and counts them.
   - The stream opens at 48 kHz (the canonical rate); a device without 48 kHz is refused with a
     latched warning.
   - A normal-priority pump thread pops the ring every few milliseconds, maps channels, and
     time-stretches with `multiview_audio::AdaptiveResampler` (same rate, ±ppm). A buffer-level
     servo (the ADR-0044 `BufferServo` shape) holds the source's `AudioStore` fill near a target,
     so device drift is absorbed within a clamped band. It publishes into an `AudioStore::live`
     store.
   - The output clock reads the `AudioStore` wait-free, as for every other source. No callback,
     a stalled device, or a lost device reads as silence (gap-free store).
2. **Output** `type = "audio_device"`.
   - The engine pushes each tick's program audio into the existing bounded drop-oldest FIFO
     (`DisplayAudioPublisher`).
   - The existing display-audio drain loop (servo, resampler, xrun machine) runs unchanged over a
     new `AlsaSink` implementation whose `write` pushes into an SPSC ring and returns at once
     (partial writes allowed). The cpal output callback pops that ring and fills any shortfall
     with silence (counted as an underrun). `delay_frames` reports the ring fill.
   - The device capability (channels, rates) comes from cpal's supported configs through an
     `EldSource` implementation, so the sink negotiates exactly as on HDMI.
3. **Device lifecycle.** Open and reopen run on a helper thread with a deadline (as for capture
   devices). A cpal error callback (device unplugged, format change) marks the stream lost; the
   pump/drain reopens with capped backoff. The engine never waits for any of it.
4. **Configuration and API.** A device is named by its exact cpal device name or `default`.
   Optional `channels`. The control API refuses to create `audio_device`
   sources and outputs (local hardware is file-configured, as for capture devices).
5. **Permissions.** macOS microphone access is per-binary TCC consent; Windows microphone access
   is the per-app privacy setting. A denied device opens but delivers silence or errors. The
   source reports this as a typed, latched warning, not a crash.

## Rationale

- **cpal** covers CoreAudio and WASAPI with one safe API, is widely used, and is permissively
  licensed. Writing our own CoreAudio and WASAPI bindings would add two unsafe FFI surfaces.
- **The SPSC ring** is the only structure that an RT callback may touch: wait-free on both ends,
  fixed size, no allocation. A mutex would let a descheduled engine-side holder stall the callback
  (priority inversion).
- **Reuse:** the AudioStore (gap-free, drop-oldest, wait-free read), the adaptive resampler, the
  servo and the xrun machine are tested already. The new code is two ring adapters and the device
  lifecycle.

## Alternatives considered

| Alternative | Rejected because |
| ----------- | ---------------- |
| FFmpeg `avfoundation` / `dshow` audio capture | No output device on either platform. Audio arrives on the demux thread with no device-clock signal, so drift cannot be servoed. One path per platform instead of one. |
| Direct `coreaudio-sys` / `windows` crate bindings | Two new unsafe FFI surfaces to keep correct; cpal already wraps both. |
| Mutex-guarded FIFO touched by the callback | Priority inversion: a preempted lock holder stalls an RT audio thread (glitches), and any shared lock couples the device to the engine side. |
| Run the device as the master clock | Breaks invariant #1: the output clock is the only master. Devices are slaved by resampling. |

## Consequences

- New optional dependencies (cpal and its platform crates, rtrb) appear only with `audio-device`.
  `cargo check --workspace` and the default build stay unchanged. `cargo deny` must pass with the
  feature graph.
- The feature is supported on macOS and Windows. cpal's Linux backend needs `libasound`; Linux
  device audio is not part of the first delivery.
- Tests: the ring adapters, pump and drain run in CI over a simulated device (a thread that calls
  the callback on its own clock, with drift, stalls, bursts and errors). Chaos/soak tests prove the
  engine tick is never delayed and every buffer stays bounded. Real-device runs happen on macOS and
  Windows test hosts.
- Invariants #1 and #10 hold by construction: the engine touches only the `AudioStore` (wait-free
  read) and the publisher FIFO (short in-memory copy); the RT callback touches only its ring.
