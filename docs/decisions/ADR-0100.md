# ADR-0100: VT clip jobs — web capture and URL fetch fill media assets; slot storage on Disk or Memory

- **Status:** Proposed
- **Area:** Media / Input / Efficiency
- **Date:** 2026-11-07
- **Source:** operator request (VT slots filled by web sources and URLs)
- **Builds on:** [ADR-0099](ADR-0099.md) (web engine), [ADR-0057](ADR-0057.md) (media library and players), [ADR-0097](ADR-0097.md) (vamp), [ADR-0058](ADR-0058.md) (NV12+A)
- **Refines:** [ADR-0082](ADR-0082.md) (render-to-VT, for page capture)

## Context

The cheapest way to show radar is to capture a loop and play it locally. Radar data changes every few minutes, so a browser held open adds nothing. Sample captures confirm the approach.

A VT slot is a media player playing a clip. It is **not** a live source and has no `activation`, `idle` or `ready` state. A job that fills it is background work.

Facts:

- `MediaAsset` holds id, kind, path, trim, vamp and EOF policy. Probed truth is runtime state, never authored.
- **The player cannot play a new clip at runtime today.** `TransportVerb::Load { asset }` exists, but the executor ignores the asset and seeks the already-open file to its in-point (`pipeline.rs:13085`). A player boots idle, with a mailbox and no store, ingest or audio plan, unless its default asset declares `out_point_frames` (`pipeline.rs:10429`).
- Config validation allows at most two media players (`multiview-config/src/lib.rs:751`, an MVP bound). Media changes are restart-class (`multiview-config/src/diff.rs:228`).
- Playback advances one frame index per decoded frame at canvas cadence (`player/transport.rs:64`, `pipeline.rs:13143`). There is no hold or variable-duration schedule.
- At non-looping EOF the executor enters a heartbeat hold and returns (`pipeline.rs:13222`).
- `TileScaler::convert` produces NV12 only (`pipeline.rs:14321`), so the player path drops alpha today, although `Nv12Image` can carry an alpha plane. ADR-0058 does not list FFV1 among verified alpha formats.
- The default FFmpeg build has no H.264 or HEVC software encoder. `libx264` used in the samples cannot ship in the default build. FFV1 (encoder and decoder), `mjpeg` and the `mov` muxer are allowlisted; `matroska` is demux-only. `h264_nvenc` exists only in the `nvidia` profile. VP9, AV1, H.264 and HEVC decoders are allowlisted, as are matroska and mov demuxers. The `webm` muxer and alpha decode paths are not in use.
- Measured FFV1 at 1280x720: 12 radar frames 4.2 MB; wind 49 MB for 6 s (about 8 MB/s). MJPEG wind: 16.5 MB for 6 s.
- Decoded 1080p NV12 is 3.11 MB per frame, 5.18 MB with alpha.
- The radar timeline labels are editorial times from Windy's UI and are irregular, about 5–8 minutes apart. Timeline positions at 1-minute resolution can show the same radar picture.

## Decision

0. **Prerequisite: a player that can change clips (R3).** Before any fill can reach air, the media player gains:
   - **Always-present slot.** Every declared player registers its store, ingest and audio plan at boot, even with no clip, and publishes a NA image until a clip is ready.
   - **Generated-asset registry.** A durable manifest, keyed by fill and player, records each promoted clip: path, probed geometry, frame count, timing, provenance and version. It is the source of truth for job output. Boot loads the newest valid version per player. Cleanup never removes an open version or the rollback version.
   - **Real load.** `Load` opens and probes the new file on a helper thread, off the ingest loop, then hands a ready, bounded handle to the executor. The executor commits video and audio together, at the next loop boundary (`play_last`) or at once (`na`), and output stamps stay monotonic from the tick counter. A newer load cancels a staged one. A failed open leaves the current clip.
   - **EOF.** A non-looping player keeps its mailbox loop alive at EOF so a later load can still commit.
   - **Player count.** The two-player bound is replaced by an admission check on decode cost. The operator has not yet said how many VT slots are needed.
   - This touches the output path. It needs a design note, a chaos test (load storms, bad files, cancel during swap) and a soak with the output cadence measured.

1. **Three fill types for a VT slot.** `file` (existing), `web_capture` and `url_fetch`. A filled slot plays through the media player once decision 0 lands. The fill definition is new config under `[[media_fill]]`, bound to one player. Fill definitions are durable desired state, managed through the API; editing a fill is a job-intent change, not a restart. Changing the set of players stays restart-class until the player work makes it live.

   ```toml
   [[media_fill]]
   id = "syd-radar"
   player = "vt-1"
   kind = "web_capture"
   template = "windy"
   refresh = { mode = "interval", minutes = 5 }   # or { mode = "one_shot" }
   during_refresh = "play_last"                   # or "na"
   storage = "disk"                               # or "memory"
   [media_fill.view]
   overlay = "radar"
   lat = -33.946
   lon = 150.370
   zoom = 10
   width = 1920
   height = 1080
   capture = "steps"                              # or "continuous"
   timing = "equal"                               # or "real"
   frame_ms = 600
   end_hold_ms = 1000
   crossfade_ms = 0
   background = "opaque"
   ```

2. **Each view is independent, with copy.** `POST /api/v1/media/fills` accepts `copy_from = "<id>"` in the UI and API. The copy is a one-time value copy with no live link.

3. **Refresh.** `one_shot` runs only on a trigger (button, API, automation), never at boot. `interval` runs on a schedule, staggered by a stable per-fill offset. The trigger endpoint is `POST /api/v1/media/fills/{id}/run`. Boot does not run a capture; a persisted last good clip loads as normal.

4. **Clip job runner.** One runner executes all jobs with a bounded concurrency (`media_jobs.concurrency`, default 1). A job is `queued`, `running`, `succeeded`, `failed` or `cancelled`, with a named phase and percent where known. Queue length is bounded; a repeat trigger for a fill that already has a job coalesces. Jobs run off the data plane, in their own resource scope (ADR-0099), and emit `media.job` events. Admission refuses a job that does not fit and retries at the next interval.

5. **Web capture.** The job opens a dedicated browser, runs the template, then closes the browser.
   - `steps`: pause, step the timeline, capture one frame per distinct data frame. Near-duplicate frames are removed by comparison with tolerance, not hash only, so a repeated radar picture cannot stall the loop.
   - `continuous`: screencast one animation cycle. Used for particle layers.
   - Frames and their timestamps are stored in the job directory, so hold or timing changes rebuild the clip without a new capture.

6. **Clip format.** The job writes constant-frame-rate video at the exact canvas rational, so the player's one-frame-per-tick model plays it correctly. Holds, end holds and crossfades are rendered into the file as repeated or blended frames. The default is FFV1 in `mov`, intra-only, for the LGPL default build; it is provisional until FFV1 playback decode cost is measured against MJPEG, and the job writer (image frames to FFV1, with rational timestamps) is new code beside the existing encoder and muxer wrappers. Transparent views write `yuva420p` only after an alpha round trip through the shipped FFmpeg is proven by pixel test. With the `nvidia` feature, `continuous` clips may use `h264_nvenc` where size matters. The job carries no audio. Encoder failure fails the job.

7. **Timing.** `equal` gives each frame `frame_ms`. `real` scales each frame by its gap to the next, normalised to the same total. `end_hold_ms` holds the newest frame. `crossfade_ms` blends the loop point; default 0 for radar and 1000 for continuous layers. Clip frame timing is rational, and output stamping stays on the tick counter.

8. **URL fetch.** The job runs `yt-dlp` as a subprocess, reusing the runtime discovery and process handling from `multiview_input::youtube`. It is never linked or bundled. It has a hard timeout, a per-job and total disk quota (`media_jobs.disk_quota_gb`, default 20), `--no-playlist`, a format selector limited to allowlisted codecs and a `--max-filesize` guard. Arguments are a literal vector with the URL after `--`, and config files are disabled with `--ignore-config`.

   **SSRF.** Checking the input URL does not protect the host, because the tool resolves names, follows redirects and contacts media hosts itself. The fetch therefore runs with restricted egress: `https` only, an operator host allowlist by default (`media_jobs.fetch_hosts`), and traffic through a filtering local proxy that re-checks each resolved address with `net_guard::screen_ip`, or a network namespace that cannot reach private addresses. If neither is available, URL fetch is disabled and the reason is shown. Progress is parsed from the tool's progress template. A partial file is resumable. A fetched format the build cannot decode fails with a named reason.

9. **Validation and promotion.** A job writes to a temporary path in the same filesystem, then validates: probe, decode one frame, frame count, duration, template validators and alpha presence where declared. Only then is it renamed to a versioned path and recorded. Atomic rename means a failed job cannot damage the last good clip. The newest N versions per fill are kept (default 2).

10. **During refresh.** User-selectable per fill:
    - `play_last`: the old clip plays until the new clip is ready, then swaps at the next loop boundary.
    - `na`: the slot shows NA from job start until the new clip is ready.
    - With no clip yet, the slot shows NA in both modes.
    - A failed job in `play_last` keeps the old clip and reports its age. A failed job in `na` keeps the slot NA and reports the failure; the previous clip stays on disk and an operator action restores it.

11. **Loop-boundary swap.** The player has no pending-swap concept today. A new `TransportVerb::SwapAtLoop(asset)` is applied by the pure transport core when the loop wraps. It must not reset the output-anchored timeline. If the slot is not looping, the swap applies at EOF. This is R3-class work touching the player and needs its own design note and test.

12. **Slot storage: Disk or Memory.** A user choice per slot. Web-filled and URL-filled slots default to Disk. The UI says Memory is for short clips used constantly or by automation, and shows decoded size when Memory is chosen.
    - Memory holds **decoded** frames with PCM audio. Playout does no decode and no disk reads.
    - A slot may store unique frames with a hold duration each; timing still comes from the tick counter. This needs a hold-aware Memory playback path, because Disk playback advances one frame per tick.
    - Alpha clips store NV12 plus a full-resolution alpha plane. Load detects alpha and fails loudly if it cannot be preserved, never flattening. Today's player drops alpha at `TileScaler`, so every alpha load fails until an alpha-preserving path exists.
    - One user-set cap covers all slots (`media.memory_cap`, default 25% of system RAM). It is a cap, not a reservation. A load over the cap is refused with sizes and never evicts another slot.
    - The check uses stored decoded size.
    - A slot is not playable until fully loaded. Loading is throttled and runs off the data plane.
    - If swap exists and locking fails, load reports it.
    - **Refresh swap:** `play_last` loads the new clip beside the old, counts both, swaps at the loop boundary, then frees the old clip. If it does not fit, the job fails with sizes and the old clip keeps playing. `na` frees the old clip first.

13. **Metadata.** Per clip, read-only through the API and available to the CG: fill id, source kind, capture time, newest and oldest frame time with zone, per-frame times, view name, overlay, location, clip status, clip age, tool version. URL fetches also carry URL, title and uploader. The clip has nothing burned in. Templates remove site branding from the clip, and CG adds branding at broadcast.

14. **API and authorization.** `GET/POST /api/v1/media/fills`, `GET/PUT/DELETE /{id}`, `POST /{id}/run`, `POST /{id}/cancel`, `GET /api/v1/media/jobs`. Every route authorizes the fill id. A create or update also authorizes the bound `player` and any `copy_from` fill as separate objects, and a load authorizes the asset as well as the player (today's load route checks only the player). `GET /media/jobs` filters rows per object. Audit records carry fill and player ids; URL, title and uploader stay out of audit `detail` and the support bundle. Secrets are never returned.

15. **Delivery order.** Each step is a separate reviewed PR:
    1. Fill config, durable fill and clip manifest, API and OpenAPI, UI shell, terms acceptance, and the job runner with accounting. No air path.
    2. Player prerequisite (decision 0): always-present slot, real load, NA, boot from manifest, opaque FFV1 writer and decode. R3.
    3. URL fetch with egress control and promotion into a slot.
    4. Web capture: CDP pipe, sandbox, Windy template and validators, one-shot then interval.
    5. Loop-boundary swap for `play_last`, with soak. R3.
    6. Memory storage, then alpha clips, each after measured budgets.

    Live web sources and pools follow ADR-0099, after the shared lifecycle lands.

## Rationale

Filling a normal media asset reuses the player, its state machine, tally and routing, and keeps the browser off the hot path. FFV1 ships in the default build and is intra-only, so seeking and loop wrap are clean. Versioned files with atomic promotion make "keep last good" structural.

## Alternatives considered

| Alternative | Rejected because |
| ----------- | ---------------- |
| Treat a VT slot as a live source with activation | A slot plays a clip; operator rejected this, and it invents states with no meaning. |
| New `SourceKind` for filled clips | Duplicates the player, its tally and its transport. |
| libx264 clips | GPL; cannot ship in the default build. |
| MJPEG default | Smaller but lossy, and FFV1 keeps alpha; a site can select it later if size matters. |
| Run browser captures in the same browser as a live view | Couples a background job to an on-air source. |
| Compressed clip in RAM | Operator chose decoded frames, for no decode at playout. |
| Evict older Memory slots | Operator rejected this; a surprise unload can take a slot off air. |

## Consequences

- FFV1 files are larger than H.264. An interval fill writes up to a few hundred MB per day before version cleanup; continuous 1080p clips can reach about 200 MB each.
- FFV1 decode at 1080p runs on the CPU per playing slot on Disk. Cost is not yet measured and must be measured before release.
- An interval fill is a recurring cost for as long as it is configured, whether or not the slot is on air. Each run shows in accounting.
- Windy radar capture depends on the operator's acceptance of site terms (ADR-0101). URL fetches depend on the operator's rights in the fetched video. The tool does not check rights.
- yt-dlp must be installed separately and kept current; it is not on PATH on mda001 today.

## How this honors the invariants

- **#1, #10:** jobs run off the data plane; the output samples the player as before. A hung job cannot stall a tick. Memory loading is throttled and off-clock.
- **#2:** a failed job leaves last-good content.
- **#3:** the player stamps from the tick counter; `real` timing only changes integer frame holds.
- **#5, #8:** decode to NV12 once, with colour tags; alpha enters at ADR-0058.
- **Licence:** default output format needs only allowlisted LGPL components; yt-dlp is a subprocess.
